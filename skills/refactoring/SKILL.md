# 리팩터링

## 보존할 동작

- 현재 구조가 만든 구체적인 문제와 바꿀 경계를 정한다. 함수나 단계를 옮기기 전에 그 책임 자체가 필요한지 판단한다. 기존 호출로 충분하면 전달용 래퍼, 호환 계층, 별도 상태를 추가하지 않는다.
- 진입점부터 구현과 소비처까지 확인한다. import 외에 재수출, 라우트 등록, 설정 키, 큐와 웹훅처럼 간접으로 연결된 경로도 변경에 해당하면 추적한다.
- 기존 호출자가 관찰하는 입력 기본값, 성공과 실패 결과, 권한, 상태 변화와 부수 효과를 비교 기준으로 삼는다. 타이밍, 실행 횟수, 순서도 동작에 영향을 주면 포함한다. 의도한 동작 변경은 별도로 드러낸다.

## 전환 순서

- 구조 변경과 동작 변경이 한 작업에 있으면 diff에서 각각 검증할 수 있게 분리한다. 이동이나 이름 변경에 무관한 로직 수정과 포맷 변경을 섞지 않는다.
- 공개 인터페이스를 바꾸면 배포 중 함께 동작해야 하는 버전과 독립적으로 전환하는 호출자를 확인한다. 호환 경로가 필요하면 누가 언제까지 사용하는지 정하고 전환을 확인한 뒤 제거한다.
- 이전 구현을 없애기 전에 남은 소비처와 등록, 재수출을 다시 확인한다. 제거 자체가 작업의 중심이면 dead-code-removal을 적용한다.

## 동작 검증

- 보존할 동작을 기존 테스트가 실제로 보호하는지 확인하고 같은 입력과 조건으로 변경 전후를 비교한다. 빈 결과와 오류, 기존 데이터, 간접 호출처럼 바뀐 경계에 해당하는 사례를 확인한다. 새 테스트는 기존 테스트로 잡을 수 없는 구체적인 회귀가 있을 때 작성한다.
- 최종 diff를 실제 호출 경로와 대조해 보존하기로 한 상태 변화와 부수 효과를 확인한다. 성능을 이유로 구조를 바꿨으면 같은 입력과 환경으로 비교한다. 전수 정리는 실제 대상마다 변경하거나 유지한 근거를 확인한다.

## indentm과 Neoscan

- 함수 리팩터링은 두 커밋으로 나눈다. 첫 커밋은 대상 함수와 해당 테스트를, 두 번째 커밋은 참조처와 해당 테스트를 변경한다.
