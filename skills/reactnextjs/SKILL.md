# React 및 Next.js

## 구현 전

- 사용자 요청과 작업 경로의 지침을 확인한다. 설치 버전과 라우터, 실행 및 검증 명령은 패키지 파일과 설정에서 확인한다. 버전에 따라 동작이 다르면 설치본 Next.js 문서와 해당 버전의 공식 문서를 따른다.
- 목적과 기존 흐름, 최소 변경 범위는 pre-code를 따른다.
- 해당 저장소에서는 [프로젝트별 지침](references/projects.md)을 읽는다. 디자인 시스템이 있으면 기존 컴포넌트, 토큰, 레이아웃과 카피를 따른다. StyleSeed가 활성 상태라면 실제 아티팩트와 규칙 번들을 확인한다.

## 상태와 Effect

- props와 state의 파생값은 렌더 중 계산하고 계산 비용이 확인될 때 메모화를 검토한다. 사용자 조작과 작업 완료 처리는 해당 핸들러에서 실행한다.
- 대상 변경으로 하위 상태 전체를 초기화해야 하면 식별자를 key로 쓴다. 마운트 수명, 닫힘 전환과 입력을 보존하면서 일부 상태만 조정할 수 있는지도 확인한다.
- Effect는 화면과 네트워크, 구독, 타이머, 브라우저 API, 위젯을 동기화한다. 프로젝트 데이터 조회 방식과 브라우저 인증 경계를 유지하고 필요한 정리를 둔다. 외부 저장소 구독에는 useSyncExternalStore를 검토한다. 서버와 첫 브라우저 렌더의 초기값을 맞추고 브라우저 저장값과 토큰은 실행 경계 안에서 읽는다. [React 공식 가이드](https://ko.react.dev/learn/you-might-not-need-an-effect)
- Effect가 등록한 콜백에서 최신 props와 state만 읽을 때 설치 버전의 useEffectEvent를 검토한다. 연결을 다시 시작하는 값은 의존성에 둔다. [useEffectEvent](https://react.dev/reference/react/useEffectEvent)
- 전수 검토에서는 실제 호출 목록을 만들고 진입점, 콜백, 상태 소유자를 확인한다. 각 호출의 제거 또는 유지 근거와 변경 후 검증을 남긴다.

## URL과 조회

- 공유, 새로고침, 북마크, 뒤로 가기로 복원해야 할 상태는 기존 URL 파서와 라우터를 쓴다. 키, 기본값과 실제 소비 경로를 확인한다.
- 같은 경로의 클라이언트 전용 쿼리는 기존 이력 정책에 맞춰 pushState나 replaceState로 바꾼다. 무관한 키를 남기고 같은 URL을 다시 추가하지 않는다. pathname이 달라지거나 서버 데이터, 권한 판단, 리다이렉트를 다시 실행해야 하면 라우터 탐색을 쓴다. [Next.js History API](https://nextjs.org/docs/app/getting-started/linking-and-navigating#native-history-api)
- 선택 항목 목록과 화면 공용 집계는 각 소유자와 갱신 조건에 맞춰 요청한다. 독립적인 집계의 완료나 실패가 목록 표시를 막지 않게 한다.

## 렌더와 배포 경계

- 데이터와 상태는 책임 있는 컴포넌트나 훅이 소유한다. 표현 전용 컴포넌트에는 값과 이벤트를 전달한다. 중첩 정의와 리스트 키가 불필요한 리마운트를 일으키는지 확인한다.
- 비용이 큰 목록과 JSX는 소비하는 UI가 마운트될 때 만든다. Portal과 CSS 숨김은 부모 계산을 생략하지 않는다. 닫힘 애니메이션과 포커스 복원을 보존한다.
- 서버 조회와 클라이언트 훅의 경계를 확인한다. 값 import와 재수출을 따라 민감한 판단과 비밀값을 서버에 둔다. 타입만 쓰면 type import를 사용하고 경계 변경 시 브라우저 빌드 결과를 확인한다.
- 로딩, 빈 결과, 부분 실패, 재시도와 중복 조작을 구분한다. 기존 디자인 시스템의 의미 있는 요소와 라벨을 사용하고 키보드, 대비, 터치 영역, reduced motion과 좁은 화면을 확인한다. 카피 변경은 접근 가능한 이름과 지원 언어에도 반영한다.

## 검증

- 정상 진입점에서 사용자에게 보이는 성공과 실패를 검증한다. 시간 의존 동작은 지원되는 가상 타이머로 예약 경로를 실행한다. Chrome에서 직접 진입, 이력 이동, 새로고침과 빠른 전환 중 해당 동작을 확인한다.
- 성능은 같은 환경과 입력에서 클릭, 선택 표시, 요청, 새 데이터 렌더를 따로 잰다. 페이지 탐색과 목록 API를 구분하고 CPU 프로파일로 병목을 확인한다. 모의 응답 조건과 실제 측정값을 구분한다.
- 프로젝트 검사로 영향 범위를 검증한다. 경로 삭제에는 dead-code-removal을 적용하고 import와 경로 문자열을 확인한다.
