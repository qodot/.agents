# 디자인과 상호작용

## 구현 전

- 저장소의 실제 토큰 정의와 CSS import, 컴포넌트 카탈로그, 레이아웃 구조, 대표 화면과 카피 가이드를 연다. 기존 컴포넌트의 공개 props, variant, size, states와 디자인 의도를 비교하고 재사용한다.
- 색, 공간, 타이포, radius, shadow는 프로젝트의 역할 기반 토큰을 사용한다. 이미 쓰는 headless primitive, 아이콘, 클래스 합성 유틸과 variant 체계를 따른다. 원시 값이나 새 토큰이 필요하면 기존 토큰이 충족하지 못하는 쓰임을 확인한다.
- 재사용하는 primitive와 도메인 표현의 책임을 분명히 한다. 상호작용 primitive에 업무 타입과 조회를 넣기 전에 기존 디자인 시스템의 경계를 확인한다.

## 화면 상태와 접근성

- 기본 상태 외에 데이터 로딩, 빈 결과, 오류와 재시도, 변경 성공, 진행 중 액션, 비활성 상태 중 실제로 발생하는 경우를 설계한다. 로딩과 빈 결과를 구분하고, 부분 실패는 영향을 받는 부분에 드러낸다. 위치와 크기가 맞는 로딩 표시로 레이아웃 점프를 줄인다.
- 폼과 버튼에는 의미에 맞는 HTML 또는 기존 접근성 primitive를 쓴다. 입력 라벨과 오류를 프로그램으로 연결하고, 아이콘 단독 버튼에는 실제 행동을 명명한다. 장식 아이콘은 보조 기술에서 제외하고, 영역이 바뀌는 동안 필요하면 `aria-busy`를 표시한다.
- 키보드로 접근, 조작, 탈출이 가능한지 확인한다. 포커스가 화면에서 보이는지, 팝업이 닫힌 뒤 올바른 곳으로 복원되는지 확인한다. 의미는 색과 함께 텍스트나 아이콘으로 제공한다. 실제 전경과 배경, 상태 조합에서 대비를 확인한다. 동작이 크거나 반복되는 효과는 `prefers-reduced-motion`을 존중한다.
- 모바일과 데스크톱에서 긴 레이블, 잘림, 넘침, 터치 영역, 스크롤과 화면 폭 변화, 안전 영역을 실제 화면으로 확인한다. 프로젝트의 토큰이나 예시로 상태를 재현한다.
- 사용자 문구는 제품별 목소리, 어미, 번역 문서가 우선한다. 버튼은 수행할 행동, 오류는 영향과 가능한 회복 행동, 빈 화면은 다음 행동을 알린다. 한 문장에 한 정보를 담고, 기존 용어를 검색해서 같은 의미에 같은 단어를 쓴다. 문구를 수정할 때 보이는 텍스트와 함께 접근 가능한 이름, 동적 레이블, 지원 언어의 딕셔너리와 테스트 단언을 확인한다. Icarus와 Huxley의 구체 규칙은 [저장소별 지침](projects.md)을 따른다.

## StyleSeed가 활성인 프로젝트

- 레지스트리 프로젝트는 `.styleseed/project.json`과 `.styleseed/artifacts/index.json`에서 대상 artifact를 정하고, 해당 `.styleseed/bundles/<artifact-id>.md`와 manifest를 읽는다. 레지스트리가 없을 때는 해당 프로젝트의 레거시 lock과 effective rules를 쓴다. 별도 작업은 기존 `styleseed` 라우터에서 종류에 맞는 첫 스킬 하나를 고른다.
- React/Tailwind v4용 `ss-component`에서는 활성 import와 토큰 파일, 실제 primitive, props와 상태를 먼저 확인한다. 적용되는 어댑터에서 `React.ComponentProps<>`, CVA, `cn`, semantic token, `data-slot`, 상태 속성, ARIA passthrough와 키보드 포커스의 기존 규칙을 따른다. 파일과 alias를 임의로 추가하지 않는다.
- `ss-feedback`의 skeleton 표시 지연과 지속 시간, 영역별 오류, action toast와 undo, `ss-motion`의 프리셋 및 reduced motion 매핑은 해당 기능 요청과 활성 규칙이 맞을 때 원본에서 확인한다. StyleSeed의 44px 터치 타깃과 대비 기준 역시 대상 어댑터와 접근성 체크에서 판단한다.
- 새 화면을 만들거나 크게 바꾸면 `ss-build`의 코드 검토와 렌더링 검증을 적용한다. `ss-review`는 코드와 토큰, `ss-a11y`는 접근성, `ss-audit`는 UX 흐름, `ss-verify`는 실제 렌더를 다룬다. 운영 데이터를 비워 빈 상태를 만들지 않는다.

## 별도 작업 방식

- 시각 방향이 핵심이면 `frontend-design`에서 타이포, 색, 공간, 모션과 기존 제품의 시각 언어를 참고한다. 기존 화면을 고칠 때는 프로젝트의 디자인 시스템 안에서 변경한다.
- 프로젝트에 코드를 만드는 일과 대화에서 설명이나 시안을 보여주는 일은 각각 프로젝트 작업 흐름과 `visualize`를 따른다. Sites에서 관리되는 작업은 Sites의 스타터, 프리뷰와 호스팅 규칙을 따른다.
