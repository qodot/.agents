# 컴포넌트, 라우팅, 데이터, 브라우저 경계

## 구성과 데이터 소유권

- 새 파일을 만들기 전에 파일명과 구현 내용 양쪽을 검색한다. 기존 페이지, 레이아웃, 데이터 제공자, 훅, 모달, API 클라이언트와 호출 순서를 확인한다. 같은 인터페이스와 결과를 제공하는 구현을 직접 재사용한다.
- 데이터 로드, 변환, 상태 변경과 사이드 이펙트는 제품의 해당 책임을 가진 컴포넌트나 훅에 둔다. 표현 전용 컴포넌트에는 필요한 값과 이벤트를 전달한다. 상태를 복제하기 전에 URL, API 캐시, 상위 컴포넌트 중 이미 값의 원본인 곳이 있는지 확인한다.
- 렌더링 중 컴포넌트 정의가 새로 생겨 리마운트되는지, 리스트 키가 항목의 정체성을 표현하는지 확인한다. 길거나 독립적인 상태를 가진 렌더링 단위는 프로젝트가 정한 기준에 따라 컴포넌트로 분리한다. 분리할 책임이나 실제 소비 경로가 있는 곳에만 추상화를 둔다.
- 화면에서 사용하지 않는 대량의 목록과 JSX는 그 내용을 소비하는 UI가 마운트되는 시점에 생성한다. 부모가 닫힌 팝업의 내용을 미리 계산하는지, Portal이나 CSS로 가린 뒤에도 계산이 실행되는지 확인한다. 위치를 옮길 때 닫힘 애니메이션과 포커스 복원, 기존 마운트 수명을 보존한다.

## Next.js 탐색과 URL

- 라우트의 실제 진입점을 먼저 찾는다. 같은 컴포넌트가 여러 `page.tsx` 또는 다른 라우트 그룹에 렌더될 수 있으니 호출부 전부를 확인한다. URL 키를 추가하거나 바꾸기 전에 기존 키의 구분자, 기본값, 읽는 곳과 검증을 대조한다.
- 목록의 상태가 공유, 북마크, 새로고침, 뒤로 가기에서 복원되어야 하면 URL을 상태 원본으로 쓰고 기존 파서와 라우터를 유지한다. 선택, 필터, 검색, 정렬, 페이지 중 어떤 값이 해당되는지는 제품에서 결정한다.
- **확인된 Icarus 사례**. 같은 App Router 화면의 `poolGroup`이나 `view`를 클라이언트의 `useSearchParams()`만 읽을 때 `window.history.pushState(null, '', href)`로 이동해 별도 페이지 요청을 줄였다. 같은 값을 다시 선택할 때 이력 추가를 피하고, 별도 발송 그룹 경로에서 오는 경우에는 `router.push()`를 쓴다. 브라우저 이력 교체가 제품 의도라면 기존 코드의 replace 동작을 따른다.
- 이 사례를 적용하기 전 검색 파라미터를 읽는 서버 `page`나 레이아웃, 서버 데이터나 재검증, 리다이렉트, 미들웨어가 있는지 확인한다. 서버 탐색이 기능에 필요한 경로는 해당 탐색을 유지한다. `nuqs` 등 프로젝트에 정해진 도구가 있으면 그 도구의 URL 쓰기, 탐색, 캐시 설정을 먼저 따른다.

## 브라우저 배포 경계

- RSC 또는 서버 전용 조회와 클라이언트 훅을 한 파일에 섞지 않는다. 클라이언트 엔트리에서 값으로 import하는 상위 barrel과 재수출을 포함해 간접 의존성을 확인한다.
- 가격 기준, 민감한 점수 산식, 비밀값, 내부 판단과 데이터 접근은 서버 모듈에서 처리한다. 화면에는 접근이 허용된 결과와 표시용 데이터만 전달한다. 라우트 접근 제한은 이미 전달된 JS의 열람을 막지 못한다.
- 단일 named import도 빌드에서 모듈 평가나 부수 효과를 끌고 갈 수 있다. 공개 가능한 상수와 표시 로직은 서버 의존성이 없는 모듈에서 가져오고, 타입만 쓰면 `import type`을 사용한다. 브라우저 경계가 바뀌면 프로젝트의 검사와 실제 클라이언트 빌드 결과에서 유출과 간접 import를 검증한다.
- API 호출은 프로젝트가 관리하는 요청 함수나 생성 타입을 따른다. 기존 응답 스키마, 권한과 그룹 소속 검사, 오류와 빈 상태, 로딩 완료 조건을 확인한다. UI가 실제로 사용할 값과 사이드바 수치처럼 별개인 값이 동시에 요청되는 경우 어느 요청이 화면 표시를 막는지 확인한다.
