# 컨벤션 픽스업

코드 작성 지침을 읽고 대상 코드를 지침과 하나씩 대조해 위반을 찾아 수정하고, fixup 커밋으로 반영한다.

## 전체 흐름

```
지침 수집 → 리뷰 대상 확정 → 준수 리뷰 → 수정 → 검증 → fixup 커밋 → 보고
```

## Phase 1: 지침 수집

두 소스를 모두 읽는다. 이미 이 세션에서 읽었으면 다시 읽지 않는다.

1. 글로벌 지침: `~/.pi/agent/AGENTS.md`
2. 저장소 지침: 현재 작업 디렉터리에서 위로 올라가며 찾은 루트 `AGENTS.md`. 대상 파일 경로의 상위에 추가 `AGENTS.md`가 있으면 그것도 포함한다.

지침 중 코드 작성 규칙만 검토 기준으로 삼는다. 문서 작성 규칙, Git 브랜치 정책 등은 검토 대상이 아니지만 수정 후 커밋 단계에서는 준수한다.

## Phase 2: 리뷰 대상 확정

- 사용자가 파일, 디렉터리, 커밋 범위를 지정했으면 그것만 검토한다.
- 지정이 없으면 `git status`와 `git diff`(staged, unstaged)로 변경된 파일과 신규 파일을 대상으로 한다.
- 대상 파일이 많으면 논리 단위로 나누어 진행하고, 각 단계 결과를 중간 보고한다.
- 이미 merge된 이력의 커밋이 아니라, 현재 브랜치의 검토되지 않은 변경분을 다룬다고 가정한다. 불명확하면 확인한다.

## Phase 3: 준수 리뷰

변경 hunk만 보지 않고 대상 파일 전체를 읽어 문맥과 함께 검토한다. 각 위반은 다음을 갖춘 항목으로 목록화한다.

- 파일 경로와 줄 번호
- 위반 내용
- 근거가 되는 지침 조항 (어느 소스의 어느 항목인지)

검토 시 주의:

- 지침에 없는 개인 취향(네이밍 스타일, 포맷 등)은 위반으로 삼지 않는다. 지침에 근거 없으면 지적하지 않는다.
- 지침끼리 충돌하거나 해석이 갈리면 수정하지 말고 항목만 정리해 사용자에게 질문한다.
- 외부 의존성 코드나 생성된 코드는 제외한다.

## Phase 4: 수정

- 기계적 수정(주석 제거, match 전환, import 정리 등)은 바로 적용한다.
- 구조 변경이 필요한 수정(함수 추출, Result 타입 전환, 파일 이동 등)은 영향 범위를 먼저 파악하고, 파일 수가 넓게 퍼지면 사용자에게 확인 후 진행한다.
- 수정마다 원래 의도를 바꾸지 않는다. 지침 준수 형태로 바꿀 뿐이다.

## Phase 5: 검증

- 프로젝트의 검증 명령을 확인해 실행한다 (예: package.json scripts의 lint, typecheck, test, ci).
- 실패하면 원인을 해결하고 다시 실행한다. 해결이 지침 위반 수정과 무관한 기존 문제면 사용자에게 보고하고 진행 여부를 묻는다.

## Phase 6: fixup 커밋

1. 수정이 어느 커밋에 속하는지 판단한다. 우선순위는 사용자 지정 커밋, 수정된 파일과 내용이 속한 최근 커밋 순서다.
2. `git log`와 `git show`로 타깃을 확인한 뒤 `git commit --fixup <sha>`로 커밋한다.
3. 수정이 여러 커밋에 걸쳐 있으면 논리 단위로 스테이징을 나눠 각각 fixup 커밋을 만든다.
4. 타깃이 애매하면 커밋하지 말고 후보와 이유를 제시해 사용자에게 확인한다.

## 보고 형식

- 위반 목록 (지침 근거 포함)
- 수정 내역 (파일별)
- 검증 결과 (실행한 명령과 결과)
- 생성한 fixup 커밋 목록 (타깃 sha 포함)
- 수정하지 않은 항목과 이유 (확인 필요, 지침 충돌 등)
