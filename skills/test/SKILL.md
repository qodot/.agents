# 테스트

## 무엇을 검증할지

- 요청한 동작과 보존할 동작을 정하고, 정상 진입점부터 기존 테스트와 fixture까지 확인한다. 공개 함수의 반환값, 명시적 실패, 실제 저장, 화면 표시나 포커스처럼 호출자가 관찰할 수 있는 결과를 검증한다. 비공개 함수, 내부 상태와 구현 호출 순서에 기대지 않는다. 요청 횟수 또는 순서 자체가 외부 동작의 요구사항이면 실제 경계에서 관찰한다.
- 새 공개 함수의 입력과 결과를 테스트한다. 테스트를 위해 헬퍼를 공개하지 않는다. 파서는 유효 입력의 정규화 결과와 잘못된 입력의 오류를 검증하며 기존 검증 수준을 유지한다.
- 제목은 한글로 입력 조건과 기대 결과를 표현한다. 제품 코드에서 그 동작을 제거하거나 반대로 바꿨을 때 실패할 입력을 고른다. 예를 들어 목록 제한은 제한보다 많은 데이터로, 유일성은 실제 저장 거절로 확인한다. SQL 문자열, 라이브러리 기본값, fixture 상수의 재확인으로 제품 결과를 대신하지 않는다.

## 외부 의존성과 계층

- 업무 코드의 네트워크, DB, 파일 시스템 의존성은 입력으로 드러낸다. 목은 주입한 외부 I/O에서만 성공과 실패를 재현한다. 모듈, 전역 객체, 프로토타입은 몽키 패칭하지 않는다. 업무 테스트는 클라이언트 메서드의 반환값을 쓰고, HTTP 요청 형식과 응답 파싱은 실제 클라이언트를 로컬 테스트 서버에 연결해 확인한다. 테스트만을 위한 전송 함수는 추가하지 않는다.
- 여러 계층의 연결과 실제 저장 결과는 통합 테스트를 우선한다. 하위 계층이 입력 조합과 경계를 검증하면 상위 계층은 대표 성공과 실패, 오류 전파, 응답 변환과 상위 계층 고유의 분기를 확인한다.
- 저장소가 지정한 테스트 환경과 DB를 사용한다. 운영 자격 증명이나 운영 DB에는 연결하지 않는다. 공통 설정은 테스트 초기화 파일에 두고, 개별 케이스는 필요한 경우만 덮어쓴다.

## 시나리오, 시간과 실행

- 같은 초기 상태, 입력, 동작으로 확인하는 결과만 다르면 한 시나리오에서 고유 검증을 모두 유지한다. 독립 분기, 경계의 양쪽, 상태 전이와 외부 결과가 다르면 따로 검증한다. 대량 fixture는 규모가 검증 대상인 계층에 두고, 삽입 순서가 중요하지 않으면 일괄 준비한다.
- 폴링, 재시도, 디바운스, 만료는 런타임이 지원하는 가상 타이머로 실제 예약 경로를 실행한다. 필요하면 경계 직전과 직후를 확인하고 실패해도 타이머를 복구한다. 타임아웃은 신호 존재와 함께 미완료 요청의 중단과 반환 오류를 확인한다. 테스트 편의를 위해 제품 대기 시간이나 검증 강도를 줄이지 않는다.
- 의존 선언, 테스트, fixture와 헬퍼 순으로 배치하되 런타임이 요구하는 설정 위치를 따른다. 변경 테스트를 함께 실행하고 공통 상태, DB, 타이머를 건드렸다면 영향을 받는 묶음까지 확인한다. 테스트 선언 수와 실행 사례 수를 구분하고 실행 시간은 같은 조건에서 비교한다. 실제 실행 명령과 결과, 미검증 범위를 보고한다.

## indentm

- 테스트는 대상과 같은 패키지의 같은 디렉터리에 .test.ts 또는 .test.tsx로 둔다. 공통 설정은 test-setup.ts, DOM 설정은 test-setup-dom.ts를 따른다. bun run test:node, bun run test:dom과 브라우저 테스트는 현재 저장소 명령을 확인한다.
- Bun 시간 제어는 bun:test의 jest.useFakeTimers()와 jest.advanceTimersByTime()을 사용한다. React 업데이트는 act 안에서 마친다. HappyDOM의 가상 타이머 전환 전에는 남은 실제 0ms 작업을 처리한다. 정리할 때 act 안에서 화면을 정리하고 가상 0ms 작업을 처리한 뒤 실제 타이머로 복원한다. 화면 타이머를 바꾸면 전체 DOM 테스트로 상호 영향을 확인한다.
- DB 검증에는 postgres-test의 localhost:5433/icarus_test만 사용한다. 스키마는 bun run db:migrate:test로 준비한다. 캠페인과 세션의 권한 변경은 저장소 AGENTS.md의 소유자, admin, 미승인 사용자, 소속 불일치와 루트 목록 조건을 검증한다. 실행과 PR 검증은 icarus-git의 현행 규칙을 따른다.

## Neoscan

- 테스트는 lib/ 경로에 대응하는 test/ 아래에 _test.exs로 둔다. ExUnit 제목은 입력의 구체 조건과 관찰 결과를 쓴다. 성공은 “입력이 XX이면 XX 반환”, 실패는 “입력이 XX이면 XX한 에러 발생”으로 적는다. 공통 설정은 config/test.exs, 초기화는 test/test_helper.exs를 따른다.
- mix test는 테스트 DB 생성과 마이그레이션을 수행한다. Spray Docker Compose의 db_test 서비스에 있는 localhost:25433/neoscan_test를 사용한다. MIX_TEST_PARTITION으로 분리할 수 있다. 공유 DATABASE_URL과 운영 DB는 사용하지 않는다.
- 테스트용 Spray 테이블은 test/support/migrations/20261023090000_create_spray_ingest_tables.exs에서 관리한다. 기존 파일을 수정하고 새 테스트 DB나 새 파티션에서 스키마 생성과 테스트를 확인한다. 운영 Spray 테이블 변경은 Spray의 Django migration을 따른다. PR 전에는 저장소 Git 스킬에서 검증 명령을 확인한다.
