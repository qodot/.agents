# 에픽 QA 요청

에픽을 테스트할 준비를 마친 뒤 ella에게 Slack으로 QA를 요청한다. QA 요청 실행에는 ella의 피처 플래그 권한 추가와 Slack 전송이 포함된다. 스킬 자체의 작성이나 수정 요청을 실제 QA 요청으로 해석하지 않는다.

## 준비와 실행

1. 대화에서 대상 에픽을 식별하고 문서를 읽는다. 저장소 문서는 `docs/epics/`에서 찾는다. 대상이 모호하면 질문한다. 메시지에 넣을 문서 링크는 해당 에픽의 GitHub 파일 링크와 실제 Notion 페이지 링크를 모두 확인한다. GitHub 파일은 원격 저장소에 존재하는 경로를 사용하고, Notion 링크는 에픽의 `notion_url` 등에서 확인한다. 로컬 경로로 대신하지 않는다. 에픽의 `assignee`로 작업자를 확인하고 해당 Slack 사용자를 식별한다.
2. 에픽 문서와 구현에서 해당 기능을 제어하는 피처 플래그 키를 확인한다. 피처 플래그 없는 에픽은 이 절차의 유효한 대상이 아니다. 키를 찾을 수 없으면 누락으로 보고하고 필요한 정보를 질문한다. 플래그 없이 요청을 보내거나, 이름을 추측해 플래그를 새로 만들지 않는다.
3. [featureflag-managing](/Users/qodot/.codex/skills/featureflag-managing/SKILL.md)을 읽고 프로덕션 관리 화면에서 ella의 서비스 계정에 해당 플래그를 허용한다. 기존 공개 대상을 유지하며 ella의 개별 사용자 권한을 추가하고, 저장 후 반영을 확인한다. 이미 개별 허용되어 있으면 유지한다. Slack의 ella와 서비스 계정의 ella를 각각 확인하고, 동명이인 등으로 식별이 불명확할 때만 질문한다.
4. 해당 기능이 프로덕션에 반영되었고 테스트 화면에 접근할 수 있는지 확인한다. 메시지에는 실제 테스트를 시작할 수 있는 프로덕션 링크를 넣는다. 특정 캠페인이나 발송 그룹이 필요하면 그 화면으로 바로 들어가는 링크를 사용한다. 링크를 눌러 테스트를 시작할 수 있게 하고, 캠페인 목록이나 홈 화면에서 다시 대상을 찾게 하지 않는다. 로컬, 프리뷰, PR 링크로 대체하지 않는다. 배포나 테스트 데이터 준비가 막혀 있으면 필요한 후속 조치를 보고하고 요청 전송을 보류한다. QA 요청을 위해 임의로 배포하지 않는다.
5. 문서의 핵심 요구사항과 실제 화면을 기준으로 테스트 방법을 아주 쉽고 짧게 요약한다. 클릭할 곳과 확인할 결과를 짝지어 적고, 구현 용어와 긴 체크리스트를 넣지 않는다. 가능하면 2~4단계로 끝내되 핵심 동작은 빠뜨리지 않는다. 이 스킬이 사용자를 대신해 프로덕션에서 발송이나 삭제 같은 업무를 실행할 필요는 없다.
6. [agent-slackbot](/Users/qodot/.agents/skills/agent-slackbot/SKILL.md)을 읽고 산나비 봇으로 `#indentm` 채널에 아래 내용을 한 메시지로 보낸다. 채널과 ella, 작업자의 Slack 사용자를 조회해 확인하고, 표시 이름 텍스트가 아닌 `<@사용자ID>`로 멘션한다. 사용자가 QA 요청을 지시했다면 초안 승인 절차를 추가하지 않고 준비를 마친 후 전송한다.

## 요청 메시지

반드시 Slack Block Kit으로 보낸다. 아래 구조와 순서를 지키고 실제 에픽의 내용으로 채운다. 작업자는 에픽 담당자이며, 봇이나 QA 담당자로 대체하지 않는다.

1. `header`: `<에픽 제목> QA 요청`.
2. `section`: `<@ella의 Slack 사용자ID> 님! *<에픽 제목>* QA 부탁드려요!`.
3. `layout`: 같은 너비의 2열 한 행.
   - 왼쪽 `section`: `*에픽 문서*` 다음 줄에 `<GitHub 파일 URL|GitHub 파일>, <Notion URL|Notion>`. 링크를 괄호로 감싸지 않는다.
   - 오른쪽 `section`: `*작업자*` 다음 줄에 `<@작업자의 Slack 사용자ID>`.
4. `divider`.
5. `layout`: 같은 너비의 2열, 세 행을 사용한다.
   - 첫 행: 왼쪽 `section`은 `*테스트 방법*`, 오른쪽 `section`은 `*테스트 완료 후*`.
   - 둘째 행: 왼쪽 `actions`에는 `테스트 화면 열기` URL 버튼, 오른쪽 `actions`에는 `피처 플래그 어드민 열기` URL 버튼.
   - 셋째 행: 왼쪽 `section`에는 번호가 붙은 테스트 단계, 오른쪽 `section`에는 `테스트가 끝나고 문제가 없으면, 위 피처 플래그 어드민에서 설정을 *전체 공개* 상태로 바꿔 주세요!`.

테스트 단계는 클릭할 곳과 기대 결과를 짝지어 짧게 적는다. 예:

```text
*1.* <화면에서 할 행동>

*2.* <다음 행동>
→ <보이면 되는 결과>

*3.* <추가 확인 행동>
→ <보이면 되는 결과>
```

### 배치와 문구

- 두 `layout` 모두 각 행의 `items` 두 개에 `width: "standard"`, `horizontal_alignment: "start"`를 사용한다. 문서와 작업자를 `fields`로 구성해 아래쪽 레이아웃과 섞지 않는다.
- `layout`의 `label`은 설명용으로 넣고, `is_label_visible: false`, `grid_lines: "none"`을 사용한다. 구분선 위아래에 빈 블록이나 별도의 안내를 끼우지 않는다. Slack 기본 여백을 사용한다.
- 테스트 화면 버튼은 단계 1, 2, 3보다 위에 둔다. 피처 플래그 버튼과 전체 공개 요청은 오른쪽의 테스트 완료 후 영역에 둔다.
- 피처 플래그 어드민 버튼 URL은 `https://icarus.spray.io/admin/featureflags/<URL 인코딩한 플래그 키>`다. 플래그 목록 대신 해당 플래그의 상세 화면으로 연결한다.
- `준비: 테스트용 수신자가 들어 있는 기존 발송 그룹을 사용해 주세요.` 같은 일반적인 준비 안내, 플래그 키 표시, 권한 허용 완료 안내는 메시지에 넣지 않는다. 테스트에 필요한 구체적인 행동은 테스트 단계에 담는다.
- `*전체 공개* 상태로`처럼 강조 구문의 뒤를 공백으로 분리한다. `*전체 공개*해`처럼 붙이지 않는다.
- 전체 공개 문구는 QA 담당자에게 하는 요청이다. QA 요청을 보내는 에이전트가 실제로 전체 공개하지 않는다.
- 모바일이나 좁은 화면에서는 열이 세로로 쌓일 수 있다. `layout` 미지원 클라이언트에도 문서, 작업자, 테스트 방법, 완료 후 안내가 보이도록 `fallback`에 `section` 블록을 제공한다. 버튼 대신 같은 URL의 텍스트 링크를 넣는다.
- 알림용 최상위 `text`에도 에픽 제목과 QA 요청 요지를 넣는다.

### 전송과 미리보기

[agent-slackbot](/Users/qodot/.agents/skills/agent-slackbot/SKILL.md)의 CLI가 `blocks`를 지원하지 않으면 산나비 봇 인증으로 Slack Web API의 `chat.postMessage` 또는 `chat.update`에 `blocks`를 전달한다. 인증값은 출력하지 않는다. 기존 메시지의 형식을 수정하는 요청은 같은 메시지를 업데이트한다.

사용자가 본인 DM으로 미리보기를 요청하면 그 DM에만 보낸다. 실제 QA 요청, ella 권한 변경, 전체 공개는 실행하지 않는다. 대상 에픽을 임의로 골라도 된다고 했다면 확인 가능한 에픽을 선택한다. 미리보기임은 헤더 아래 `context` 하나로 표시하고, 실제로 확인하거나 실행하지 않은 배포 상태와 권한을 완료했다고 쓰지 않는다.

전송 성공 여부와 반환된 블록 구성을 확인하고 사용자에게 보낸 메시지의 Slack 링크를 보고한다. 전송 결과가 불명확하면 기존 메시지를 확인한 뒤 재시도해 중복 요청을 피한다. 권한 추가 후 전송에 실패했다면 권한 반영 상태와 전송 실패를 구분해 보고한다.
