# 코드 작성 전 판단

## 요청을 관찰할 수 있는 결과로 바꾼다

- 최초 목적, 이후 정정, 현재 승인된 범위를 대조한다. 정상 진입점의 기대 결과와 기존 호출자가 의존하는 동작을 확인한다. 제안된 구현 방법이 목적에 맞는지 판단한다.
- 코드와 자료를 먼저 확인하고, 결과를 바꾸는 정책이나 권한을 사용자만 결정할 수 있을 때 묻는다. 이유만 묻는 요청은 근거를 조사해 답한다.

## 실제 흐름과 변경 근거를 확인한다

- 적용 지침을 확인하고 사용자가 지정한 비교 대상을 먼저 읽는다. 같은 기능의 진입점부터 호출부, 의존성, 데이터와 상태 변화, 성공과 실패, 실제 외부 작업과 테스트를 따라간다.
- 문제가 있다면 직접 원인과 그 원인을 만든 전제나 설계 선택을 구분한다. 오류 로그, 실제 코드, 외부 API 동작을 근거로 삼는다. 테스트에서 임의로 만든 상태는 실행 가능한 제품 경로와 대조한다. 성능 개선은 병목과 측정 기준을 확인한 뒤 시작한다.
- 설정, 플래그, 라우트 또는 환경 변수의 키를 바꾸기 전에 같은 종류의 기존 키, 기본값, 실제 소비처, 테스트를 확인한다. 관리 화면에서 변경과 삭제가 가능한지도 관련 작업에서 확인한다.

## 필요한 변화만 설계한다

- 목적에서 필요한 상태 변화, 최소 외부 작업, 실제 판단, 코드 구조 순서로 내려간다. 같은 처리는 기존 함수를 직접 재사용한다. 새 상태, 요청, 래퍼, 모델, 절차가 필요하면 기존 경로로 충족되지 않는 요구사항을 특정한다. 기존 코드에 있다는 이유만으로 새 경로에 같은 단계를 추가하지 않는다.
- 방어 로직, 재조회, 예외 분기, 잠금이나 재시도 처리를 더하기 전에 초기 상태, 실제 호출과 변경 순서, 최종 결과, 위반되는 요구사항을 확인한다. 기존 경계에서 이미 보장하는 조건을 다시 검사하지 않는다. 인접 코드에서 발견한 위험은 그 위험이 현재 목적을 막는지 판단한다.
- 리팩터링은 바꿀 구조와 보존할 동작을 확인한다. 기존 흐름이 요구사항을 충족하면 검토를 마친다. 단계의 필요성을 지적받으면 그 단계의 전제와 인접 단계까지 다시 본다.
- 권한, 데이터 일관성, 서버와 브라우저의 실행 경계, 운영 설정에 영향이 있는 경우 해당 책임과 기존 제약을 확인한다. 함수 구조와 시그니처는 function, React와 Next.js의 렌더 및 상태 경계는 reactnextjs, 테스트 방법은 test와 프로젝트의 검증 지침을 따른다.

## 코드를 쓰기 전에 확인할 결과를 정한다

- 성공과 실패, 변경 후에도 유지해야 할 동작을 정상 진입점에서 어떻게 확인할지 정한다. 기존 테스트가 보호하는 범위를 읽고, 변경이 깨뜨릴 수 있는 동작을 실제로 구분하는 입력과 관찰 결과를 고른다.
- 변경이 여러 호출 경로나 외부 작업에 걸치거나 선택에 따라 결과가 달라지면 목적, 확인한 근거, 재사용할 흐름, 변경 범위와 검증 방법을 코드 작성 전에 짧게 남긴다. 명확한 국소 변경은 필요한 확인을 바로 수행한다. 실제로 필요한 승인 조건은 작업 경로의 지침을 따른다.
