# 함수 작성과 리뷰

## 함수의 필요성

코드 작성 전 목적, 선례와 수정 범위는 pre-code를 따른다. 새 함수는 기존 호출로 충족할 수 없는 독립적인 연산이 있을 때 만든다. 함수나 단계의 필요성을 지적받으면 그 구조를 만든 전제와 인접 단계까지 확인한다.

## 책임, 이름, 시그니처

- 조회, 추출, 변환, 도메인 판단처럼 독립적인 의미가 있는 연산을 분리해 호출부에서 조합한다. 클라이언트 호출만 전달하는 래퍼, 같은 시그니처를 반복하는 중간 함수, 함께 쓰인다는 이유로 독립적인 결과를 강제로 묶는 함수를 피한다. 함수 길이와 사용 횟수만으로 분리하거나 공용 모듈에 옮기지 않는다.
- 같은 책임과 처리 흐름에는 같은 분리 기준, 분기 구조, 명명 방식을 쓴다. 구성이 다르면 책임, 입출력, 실행 환경이나 의존성에서 근거를 찾는다. 헬퍼는 도메인 책임을 가진 모듈에 두고 실제 외부 소비처가 생길 때 공개한다.
- 이름은 실제 입력 대상과 수행하는 동작을 드러낸다. 단건 조회에는 get, 여러 건에는 list, 입력에서 값을 찾아 꺼내는 연산에는 extract, 검증하며 해석하는 연산에는 parse를 기본으로 삼는다. 답장 여부를 판단하지 않고 메시지 하나를 읽는 함수라면 `getMessage`로 짓는다.
- 같은 연산의 처리 방식만 달라지면 명시적인 옵션을 검토한다. 책임이나 결과의 의미가 달라지면 별도 연산으로 표현한다. 같은 원본의 여러 값을 추출한다면 공통 입력 형태를 먼저 검토하고 전처리에서 후속 연산에 필요한 정보를 보존한다.
- 기존 타입으로 의미를 보존할 수 있으면 재사용한다. 읽는 필드가 적거나 목을 만들기 쉽다는 이유로 타입을 다시 정의하지 않는다. 필요한 외부 의존성과 업무 입력을 시그니처에 드러낸다. 연결 설정과 인증은 소유 계층에 두고 테스트만을 위한 전송 경계를 만들지 않는다.

## 입력, 결과, 외부 작업

- 외부 입력 경계에서 파싱한다. 파서의 성공 값에 실제로 검증한 조건과 정규화 결과를 보존하고 소비 함수는 그 성공 타입을 받는다. 타입 단언으로 검증을 대신하거나 파서와 하위 함수가 이미 보장한 조건을 다시 검사하지 않는다. DB 상태와 권한처럼 파싱으로 보장할 수 없는 조건은 소유 계층에서 확인한다. [Parse, don’t validate](https://lexi-lambda.github.io/blog/2019/11/05/parse-don-t-validate/)
- 공개 입력 파서는 도메인의 parser/에 두고 `parseSendMessageInput`처럼 대상 함수와 이름을 맞춘다. 공개 export는 `parser/index.ts`에 모은다. 비공개 파서와 전용 타입은 사용하는 함수와 같은 파일에 둔다. TypeScript에서 Zod와 Result를 쓰면 스키마, 추론 타입, 오류 타입, 함수 순으로 선언하고 정규화된 값이나 오류를 반환한다.
- 메시지와 오류처럼 종류가 정해진 값은 패턴 매칭으로 모든 경우를 처리한다. 지원되는 언어에서는 분기 누락을 컴파일 시점에 검사한다.
- 미조회, 거절, 외부 오류처럼 호출자가 다르게 처리하는 결과를 구분한다. 상태를 바꾸는 함수는 실패 위치, 재시도, 동시 실행 시 관찰되는 결과를 확인한다. 방어를 추가하기 전에 위반되는 요구사항과 구체적 실행 순서를 적는다.
- 순수 계산과 외부 작업을 구분하고 필요한 곳에서 기존 조회, 저장, 전송을 직접 호출한다. 권한, 트랜잭션, 직렬화, 네트워크 연결은 기존 소유 계층에 둔다. HTTP 경계는 도메인 입력 스키마를 재사용하고 오류와 성공값을 응답으로 변환한다.

## 검증

- 정상 진입점에서 지원하는 입력과 기존 데이터를 대조하며 성공과 실패를 확인한다. 파서를 바꿨으면 성공 반환 타입, 호출부가 넘기는 값, 소비 함수의 입력 타입을 함께 확인한다.
- 테스트에서 공개 함수의 반환, 명시적 실패와 외부에서 관찰되는 결과를 확인한다. 목이 필요하면 주입받은 외부 I/O에서 성공과 실패를 재현한다. 내부 호출 여부나 횟수, 순서로 외부 동작 검증을 대신하지 않는다. 저장소가 요구하는 공개 함수 테스트를 함께 작성한다.
- 최종 diff를 선례와 비교해 책임 분리, 분기, 이름의 일관성과 바뀐 요청, 상태, 완료 처리가 요구사항에 맞는지 확인한다. PR에는 직접 재사용한 흐름과 의도적인 차이를 실제 함수 이름으로 적는다.

## indentm repository

- 도메인의 repository/가 DB 읽기, 쓰기와 예외 변환을 맡는다. 첫 인자는 `db: Database | DatabaseTransaction`, 입력은 그다음이다. 조회는 엔티티 단위로 Result를 반환하며 단건 미조회와 DB 실패를 구분한다. 필요한 결과 조합은 업무 함수에서 수행한다.
- 트랜잭션은 `packages/core/src/db/transaction.ts`의 transaction을 사용한다. 성공 Result는 커밋하고 실패 Result나 예외는 롤백한다. 예외 변환은 onError에 둔다.

권한 정책, 구체적인 파일 배치와 실행 규칙은 작업 경로의 AGENTS.md와 프로젝트 스킬을 따른다. React의 상태와 Effect는 reactnextjs를 적용한다.
