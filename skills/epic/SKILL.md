# 제품 기획서 작성

실제로 해결할 문제와 필요한 동작을 정확하게 정의한다. 내용을 풍성하게 만들기 위해 기능, 절차, 정책과 섹션을 늘리지 않는다.

## 저장 위치와 PR 제목, 본문

- 기획서와 에픽 문서는 저장소 루트의 `docs/epics/`에 작성한다.
- PR 제목은 문서 제목 앞에 `epic: ` 접두사를 붙여 `epic: 문서 제목` 형식으로 작성한다.
- 해당 문서의 PR을 작성할 때는 기획서 전문을 PR 본문에 그대로 적는다. 요약이나 문서 링크로 대체하지 않는다.

## 현재 상태에서 출발한다

- 사용자가 준 대화, 문서와 후속 정정을 함께 읽는다. 초기 원안보다 이후에 바뀐 결정과 현재 지시를 우선한다.
- 이미 제공되는 기능, 이번에 바꿀 기능, 새로 필요한 기능을 구분한다. 현재 동작이 중요한 판단 근거라면 코드, 공개 페이지 등 실제 소유 자료를 확인한다.
- 사용자의 새로운 요구를 기존 동작인 것처럼 적지 않는다. 기존 기능을 확인하지 않은 채 새 제한이나 절차를 추가하지 않는다.
- 완료된 작업은 배경으로 내린다. 예를 들어 최초 공개가 끝났다면 이를 아직 해결해야 할 문제로 두지 않는다.
- 제목도 현재 남은 일을 표현한다. 넓은 이름보다 편집, 발행, 조회처럼 실제 행동이 드러나는 이름을 고른다.

## 문제와 해결을 짝짓는다

- 무엇을 만들지보다 누가 무엇을 할 수 없어 어떤 문제가 생기는지 먼저 쓴다.
- 서로 다른 사용자나 목적의 문제는 분리하고 각각 해결책을 붙인다. 함께 구현된다는 이유로 하나의 문제로 묶지 않는다.
- 제공해야 할 요구사항을 모두 현재의 결함으로 둔갑시키지 않는다. 현재 불가능하다는 근거가 없으면 문제라고 단정하지 않는다.
- 문제는 원인과 영향을 설명하고, 해결은 필요한 상태 변화나 사용자의 행동으로 표현한다. 기능 이름만 문제와 해결 양쪽에서 반복하지 않는다.

## 최소한의 필요한 동작을 정한다

- 사용자의 목적, 필요한 상태 변화, 사용자의 행동 순서로 요구사항을 도출한다. 기존 구현 단계나 함수 구성을 그대로 요구사항으로 옮기지 않는다.
- 기존 로그인과 권한, 편집기 등을 활용할 수 있는지 먼저 확인한다. 이메일 도메인 제한 같은 별도 정책을 임의로 끼워 넣지 않는다.
- 초안 저장, 승인, 미리보기, 수정 이력, 복원, 정정 정책 등을 관성적으로 추가하지 않는다. 실제 목적이나 명시된 제약에 필요한 경우에만 포함한다.
- 같은 목적을 직접 해결할 수 있으면 중간 절차를 줄인다. 예를 들어 일정 변경이면 취소 후 재예약부터 요구하지 말고 날짜를 바꾸는 것으로 충분한지 판단한다.
- 미정 사항은 결과를 바꾸는 실제 정책만 남긴다. 스스로 추가한 기능의 필요성을 사용자에게 판단받으려고 확인 항목을 만들지 않는다.
- 사용자가 지정한 제한은 정확히 반영한다. 예를 들어 공개 후 수정 불가가 결정되면, 공개 일정 변경과 개정 흐름에도 모순 없이 적용한다. 특정 사례의 정책을 다른 기획서에 자동으로 적용하지 않는다.

## 행동 순서로 짧고 정확하게 쓴다

- 로그인, 목록, 편집, 이용자 화면처럼 사용자가 작업하는 순서로 묶고, 각 항목 아래에 필요한 동작만 적는다. 이 순서나 항목을 모든 제품의 고정 틀로 강제하지 않는다.
- 목록에 상태별 분류, 필터, 날짜 열 등을 자동으로 늘리지 않는다. 목록을 보고 최신 항목을 구분하는 것만 필요하다면 거기까지만 쓴다.
- 짧게 쓰되 대상과 범위를 잘못 한정하지 않는다. '최신 버전을 확인한다'와 '전체 버전 목록에서 최신 버전을 구분한다', '첫 버전만 편집한다'와 '선택한 문서를 불러와 개정한다'는 다른 동작이다.
- 새 버전 작성과 기존 버전 수정을 구분한다. 편집 대상, 저장 결과와 공개되는 대상이 문장마다 달라지지 않게 한다.
- 유저 플로우는 실제 행동의 연결로 쓴다. 단순한 흐름이면 한 줄의 순서로 충분하다. 요구사항을 검증하는 절차를 사용자의 업무 흐름에 끼워 넣지 않는다.

## 섹션의 역할과 작성 범위를 지킨다

- 기본은 문제와 해결, 배경, 요구사항, 유저 플로우와 범위다. 관리 대상이나 참고 링크 등은 실제 도움이 될 때만 보탠다.
- 기존 에픽과 같은 형식을 요청받으면 관련 문서를 읽고 길이, 말투와 구조를 맞춘다. 불필요한 중복이나 구현 설명까지 답습하지 않는다.
- 요구사항은 한곳에 모은다. 전달 요구사항처럼 일부만 다른 섹션에 흩어 두지 않는다.
- 기능 목록, 완료 기준, 요약이 기존 내용을 반복하기만 하면 만들지 않는다. 별도 섹션은 작업 분할, 독립적인 성공 지표처럼 추가 목적이 있을 때만 둔다.
- 기획서에는 필요한 사용자 동작과 결과를 쓴다. 저장 포맷, 라이브러리 설정, API 경로, DB 구조와 보안 처리 방법 등 구체적인 구현은 요청받았을 때 기술 설계로 다룬다.
- 사용자가 편집 방식이나 앱과 공개 페이지의 책임을 정했다면 필요한 수준에서 반영한다. 그 결정을 설명하려고 별도 설계 절차나 중복 섹션을 만들지 않는다.

## 정정을 문서 전체에 반영한다

- 전제가 바뀌면 해당 문장만 고치지 않는다. 제목, 문제 정의, 요구사항, 유저 플로우, 범위와 참고 자료에 남은 이전 전제까지 대조한다.
- 기존 원본을 최초 자료로 삼지 않기로 했다면, 그 원본 링크와 이전 여부 논의도 제거한다. 참고 자료를 관성적으로 보존하지 않는다.
- 사용자가 수정이나 반영을 요청했거나 진행 중인 작성 작업을 정정하면 이미 승인된 문서에 직접 반영한다. 이유만 묻는 경우에는 이유를 답하고, 요청하지 않은 편집은 하지 않는다.
- 연결된 문서는 현재 내용을 읽은 뒤 필요한 부분을 수정한다. 작업 목록, 관계, 사용자 편집 등 요청과 무관한 요소를 보존하고, 반영 후 문서의 일관성과 변경 결과를 확인한다.
- 결과는 바뀐 핵심과 실제 미정 사항만 짧게 보고한다. 이미 승인된 편집을 다시 허락받지 않는다.

## 제출 전 점검

- 완료된 일을 아직 문제나 할 일로 쓰지 않았는가?
- 각 문제에 대응하는 해결이 있고, 별개의 문제를 뭉치지 않았는가?
- 실제로 없는 기능이나 사용자가 요구하지 않은 정책을 끼워 넣지 않았는가?
- 대상과 범위가 정확하고, 기존 버전과 새 버전을 혼동하지 않았는가?
- 같은 요구가 여러 섹션에서 반복되지 않는가?
- 기술 설계가 제품 요구사항을 덮지 않았는가?
- 후속 정정과 모순되는 문장이나 불필요해진 참고 자료가 남지 않았는가?

이 점검은 작성 과정에서 수행한다. 사용자가 요청하지 않았다면 점검표를 기획서에 붙이지 않는다.
